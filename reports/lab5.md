# Lab5：多线程资源死锁检测

## 实现概述

实现进程级死锁检测开关。mutex 与 semaphore 维护实际持有者和等待者，每次申请前对新增请求做试算：从可用资源开始寻找能结束的线程，假设其归还持有资源，反复推进。存在无法结束的活线程则拒绝请求并返回 -0xDEAD，拒绝时不修改实际队列。保留跨页 get_time。

## 设计与修改

- `task/process.rs`：进程控制块加入 deadlock_detect，创建和 fork 默认关闭；0/1 开关只作用于当前进程。
- `sync/deadlock.rs`：从真实资源采样 Available、Allocation 和 Need，对请求者增加一次临时需求。已退出线程不当作能归还资源的活线程。
- `sync/mutex.rs`：自旋锁记录持有者与让出 CPU 的等待者，阻塞锁记录持有者与等待队列；解锁时先转移所有权再唤醒，避免错误地把已预留的资源当成空闲。
- `sync/semaphore.rs`：记录每个线程真正获得的资源数，负计数只反映等待者数量，可用资源取 max(count,0)；唤醒前登记资源转移。up 可由不同线程调用，未持有者发信号不会把持有数减成负数。
- `syscall/sync.rs`：检查资源 ID，锁与 down 前试算；非法开关参数返回 -1，只有试算通过才调用真实原语。
- `mm/page_table.rs`、`mm/mod.rs`、`syscall/process.rs`：保留安全跨页写时间，其他前章扩展按本章官方要求无需迁移。

## 问答

### 主线程退出的资源回收

需要回收线程的用户栈、陷阱上下文、线程 ID、进程地址空间与页帧、文件描述符引用、内核栈及控制块。线程可能被就绪队列、计时器、同步原语等待队列、进程任务表和处理器引用。必须移除外部就绪/计时器引用，防止死线程再获调度；进程内同步对象和任务表也需释放以打破持有关系。当前正在使用的内核栈不能立即释放，需要先切换到其他控制流。框架用 stopping 队列延迟处理主线程内核栈。

### 两种阻塞 mutex 写法

第一种 lock 在唤醒后重新循环竞争，unlock 先将 locked 清为 false 再唤醒；新线程可能抢走锁，原等待者又睡下，存在公平性问题，必须配套循环检查。第二种 unlock 有等待者时保持锁定并直接交给该等待者，lock 被唤醒后直接返回；持有权交接是其正确性前提。若把“直接返回”与“先清空锁再唤醒”混用，就可能让两个线程都以为自己拿到锁。本实现采用直接交接，并同步更新 owner。
